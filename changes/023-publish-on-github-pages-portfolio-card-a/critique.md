**The guard** (`proposed/pages.yml`):
- *Can it be fooled?* I found no way. Fork pull requests are excluded twice: by `event == 'push'`, and because their head_sha would not equal main's tip. A re-run of an older green run carries the old head_sha and is refused. The SHA is hex, so interpolating it into the shell is safe. Only people with write access can push to main or re-run a workflow. `tests.yml` runs on every push with no `paths-ignore`, so no main commit is left without a tests run that could deploy it. Its `cancel-in-progress` turns a superseded main run into `cancelled`, which the `success` condition rejects.
- *Race (benign).* main can move after the guard passes, while the build and upload run (about a minute). The newer commit still needs its own full suite, which takes minutes, and its Pages run queues behind the older one in `concurrency: pages`, so it deploys last. The end state is always the newest tested head.
- *Fail-safe.* Yes. Actions runs `run:` under `bash -eo pipefail`. If `git ls-remote` fails, the assignment fails, the step goes red and every later step is skipped. An empty or odd result does not match, so nothing deploys. Each failure mode either deploys nothing or turns the run red.
- *Skipped deploy leaves the run green, with a `::notice::`.* That is acceptable: refusing a stale commit is correct behaviour, not a failure, and a red run would train people to ignore red. See item 1 for one side effect.
