VERDICT: REVISE
1. [major] Areas miss files the children must create. "Areas. Every child: `src/features/generator/**`, `tests/**`, `docs/data-model.md`. a also: `.gitattributes`, `research/r2-synthetic-text-realism/**`." The repo has no `requirements.txt`, no `.venv`, no `src/` and no `tests/` yet. a's "AI-text script" needs `anthropic`. The TF-IDF baseline test needs `scikit-learn`, and probably `pandas`. AGENTS.md says the stack uses a pinned `requirements.txt`, so some child has to create it, and no child's areas include it. The pre-commit gate will flag it. In the same way, the project's build command is `python -m akg build`, but no child owns an `akg` entry package (`src/akg/` or similar), or any package config needed for `python -m` to find `src/features/generator`. -> Add `requirements.txt` to a's areas, pinning only approved packages. Either add the `akg` entry module / package path to a's areas, or say that a's entry point is `python -m src.features.generator` (or similar) and that E3 wires it into `akg build`.
2. [minor] Leftovers from the removed split-node design. "Each child adds to `docs/data-model.md` ... answer-key schema and split rule (c, d)": there is no longer a split rule. Also: "every published ... IA taxonomy node appears in the answer key exactly once (taxonomy: at least once)". `taxonomy_map.csv` now gives exactly one target per node, so "at least once" contradicts the line above it and weakens the test. -> Drop "split rule". Make the taxonomy check "exactly once".
3. [minor] The consistency rule is undefined when a cluster holds ERM duplicates. "every cross-source risk cluster's IA risks have the ERM risk's L3 node as `true_erm_node`". A cluster can hold two ERM risks (a within-ERM duplicate) and an IA risk. If the two ERM risks sit under different ERM L3 nodes, the rule has no single answer, and the test either crashes or passes by whichever row it reads first. -> State that all ERM risks in one cluster sit under the same ERM L3 node, and test that. Or state which one wins.
4. [minor] The rising-L1 scenario does not say which taxonomy it counts or how an issue gets an L1. "one L1 category's issue count rises at least 50% from year 1 to year 3". IA issues link to IA risks and controls (IA L1). Other issues link to ERM items (ERM L1). INV-4 allows an issue to link only to a control, and orphan controls mitigate no risk, so some issues have no L1 at all. A test and E3's query could then count different things and both "pass". -> Say the count uses the ERM L1, with IA items placed through `true_erm_node` (or through E2's mapping in E3). Say how a control-only issue gets its L1 (through mitigates), and that issues with no risk path are excluded. Record this definition in scenarios.csv and in `docs/data-model.md`.
5. [minor] Audits are not tied to what they cover. "Audits test IA controls only ... and cover auditable entities". Issue linking now constrains issues to tested controls (good). But nothing ties an audit's `tested` controls to its `covered` entities: no requirement that tested controls mitigate a risk that some covered entity is `exposed_to`. A random generator passes every listed test. An auditor following audit -> entity -> risk -> control on the page would then see a nonsensical scope, which hits the milestone's riskiest assumption. E3's coverage and stale-coverage rounds would also measure noise. -> Add a rule and test in e: every tested control mitigates at least one risk that a covered entity is exposed to.
6. [minor] RNG stream stability across children. Committed AI text is frozen per child ("c risks, d controls, e issues ... then freezes its counts"), keyed by an internal key and checked against a hash of template inputs. Suppose one seeded RNG stream is shared. Then d drawing control attributes, or e drawing audits, before or between the earlier draws shifts c's risk inputs, and c's frozen text fails its hash. That forces API regeneration and moves the F1 baseline, though no count changed. -> Require one independent sub-seeded RNG per entity type (or per child), derived from the master seed, so later children never perturb earlier outputs. Add a test: c's risk CSVs are byte-identical before and after d's code runs.
7. [minor] The quota test's source is wrong for most counts. "Counts within ±10% of the targets in `docs/data-model.md` ... One test checks all of these from the answer key." The answer key holds risks and controls only. Auditable entities (80), audits (75), issues (250), people (120), systems (30) and regulations (15) are not in it. The only test named for those types is "at least one row". -> Have the count test read the published CSVs for all target sizes, and keep the answer key for the overlap, duplicate and orphan ratios.
8. [minor] The gate outcome is not defined for a partial pass. "the owner marks each entity type realistic / not realistic ... recorded ... as GO." The plan does not say what happens if some types are marked not realistic: whether a is revised and re-reviewed, whether b may start with those types flagged, or whether that counts as NEEDS-CLARIFICATION. -> State the rule. For example: GO only when every entity type is realistic; otherwise a is revised (`capitan revise`) and the pack is re-reviewed.
