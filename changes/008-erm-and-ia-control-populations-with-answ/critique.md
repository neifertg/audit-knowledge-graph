VERDICT: REVISE
1. [blocker] AC-1's overlap band cannot be met by the control model in Data impact. The plan says "A control cluster is the same (risk instance, control kind) in both sources" and "ERM keeps about 1.6 per risk, IA about 2.6". So an IA control can match only if its risk instance is held by both sources, and each matched pair uses one ERM control. A seed-42 full build today has 90 matched IA risks, 77 ERM-only risks and 13 within-ERM duplicates. At 1.6 ERM controls per instance, the 90 matched instances carry about 144 ERM controls, which allows at most about 144 matched pairs. That is 33-40% of 360-440 IA controls, against AC-1's "55-65% of IA controls share a true cluster with an ERM control". Reaching 55% of 360 needs at least 198 ERM controls on those 90 instances (2.2 each). That leaves about 70-110 controls (after orphans) for the 77 ERM-only risks, if each mitigates one risk. AC-2 still requires "every risk is mitigated by at least one control". It may fit the 270-330 range, but only with a skewed allocation the plan does not state. -> Before approval, state the allocation that meets AC-1 and AC-2 together, and show the arithmetic in Data impact: controls per ERM instance for matched vs ERM-only instances, and whether a duplicate ERM risk shares its original's controls. Alternatively, let generic ERM controls mitigate several risks (many-to-many, as the ER diagram allows and real RCSAs do), and say how clusters are defined then.
2. [major] The obvious fix for finding 1 creates a structural shortcut, the same trap child c's first two critiques caught for exposure. Suppose matched ERM instances get about 2.2+ controls and ERM-only instances about 1. Then the number of controls on an ERM risk shows whether that risk has an IA match: "ERM risks with 2 or more controls are matched" becomes a published-file cue for *risk* matching, outside every band 007 measured. The same holds for kinds: if ERM-only instances get only the theme's specific control, "has a generic control" reveals a match. AC-5 says "Matching controls through already-matched risks is the intended graph strategy ... and is not capped". That is fair for controls, but nothing bounds the reverse direction, controls revealing risk matches. -> Draw control counts and kinds per instance from one distribution, whatever the match status, and meet AC-1 another way (for example many-to-many generic controls). Or add an AC-5 item: a baseline that predicts whether an ERM risk (or an IA risk) has a cross-source match from its control count and kinds alone scores F1 no better than the base rate plus a stated margin, and child c's AC-5 (b) combined baseline, re-run with that cue added, still stays at or below 0.80.
3. [major] The shared-system scenario is already true by accident, so planting it proves nothing, and AC-2 leaves the scenario's membership undefined. On today's seed-42 full build, before any change, 20 of 23 systems that IA controls use, and 23 of 23 that ERM controls use, already reach 3 or more auditable entities through control -> mitigates -> risk -> exposed_to. ERM's business-unit-wide exposure and stale links inflate the ERM side. AC-2's "at least 3 systems are depended on by controls of 3 or more auditable entities" therefore passes before any code is written. "answer_key/scenarios.csv lists those systems" does not say whether it lists 3 systems or all 20+. E3 checks that "each query finds what was planted", so a blast-radius query would return far more than scenarios.csv holds, or scenarios.csv would list nearly every system. -> Define the path (for example IA controls only, through IA exposure, which is one entity per risk) and make the planted systems stand out (for example, the listed systems reach at least N entities and every unlisted system reaches at most N-2). Test that scenarios.csv equals the set computed from published files, not merely that it holds 3 or more rows.
4. [major] AC-5 checks attribute and system cues alone, never combined with text, except (c). That is the gap child c's critiques 1 and 2 found for exposure. AC-5 (a), "same type, nature and frequency", has about 2x2x6 combinations across roughly 700 controls, so its precision is tiny and the test passes for any generator. The same goes for (b) in most designs. The cue that matters is the combination: same theme subject plus the IA audit-area name. Child c bounded that for risks with its entity-mention baseline (007 AC-5 e) and its combined business-unit baseline (AC-5 b), and this plan's AC-7 tightens both for risks. Controls get no analogue, even though the plan says each control carries "its instance context (ERM business terms, IA audit area)". Child c's fifth critique (finding 3) asked for exactly this rule for controls. Regulations (`requires`, set per theme in both sources) are another cue nobody measures. -> Add to AC-5 for controls: (d) an entity-mention baseline, with the same token rule AC-7 adopts, taking the best TF-IDF candidate at its own best threshold, F1 at most 0.80; (e) TF-IDF restricted to pairs with equal type, nature and frequency (or a shared regulation), F1 at most 0.80. State in Data impact that ERM control context phrases never use a distinctive token of the entity name, as for risks.
5. [minor] AC-5 (b) and (c) are undefined when ERM lists no systems, and the plan says it often does not ("ERM lists systems for only some controls"). If an empty set counts as "the same set", (b) pairs every ERM control that has no systems with every IA control that has none, and F1 is about 0 by construction. In (c), an IA control whose ERM match lists no systems has no candidate, so recall is capped and the 0.80 ceiling is easy to pass. -> Define (b) on non-empty sets only. Define (c) so that ERM controls with no systems stay candidates (for example, "share a system, or list none"), or measure (c) only over IA controls whose candidate set is non-empty, and report that set's size.
6. [minor] Duplicate ERM risks and orphans are not placed in the cluster model. "A control instance is (risk instance, control kind)": does a within-ERM duplicate risk get its own controls? If it does, two ERM controls share a (risk instance, kind) cluster, and they could be identical rows (same context, same kind). That is within-ERM control duplication, which Out of scope excludes. Today a duplicate shares its original's control. Orphans are "controls written for instances that source does not hold". If an IA orphan is written for an instance ERM holds, under a kind ERM also lists, the rule puts it in a cross-source cluster, with no `mitigates` link to reach it. -> State both rules: duplicates share the original's controls, and orphans are never in a cross-source cluster (or say that they can be). Add to AC-3: no cluster holds two ERM controls.
7. [minor] Child a's "no shared sentence" leakage rule and AC-4's exact-text bound depend on the generic library having separate ERM and IA wording. The plan describes one library ("each worded with the theme's subject ... and the instance's context") and does not say that ERM and IA phrase a kind differently. Eight kinds times 56 subjects shared across sources is the "template sentence" risk the epic warns about. -> Say that each generic kind has a brief ERM wording and a detailed IA wording with no sentence in common. AC-1's two-times word rule and AC-4 then test it.
8. [minor] AC-1's "no matched pair is equal on all of owner, frequency and type" is always true while "owners always differ (as now)". Only the 15% clause tests attribute disagreement. Separately, a matched pair that disagrees on *type* (preventive vs detective) is the same control recorded inconsistently, which reads oddly to auditors. Frequency or nature disagreement is the realistic kind. -> Optional: give the 15% band to frequency or nature, or keep type disagreement rare. No criterion change is needed for the vacuous clause, but it should not be counted as evidence.
