VERDICT: REVISE
1. [major] The plan never says which description the build publishes while R2 is open. It builds templated text and AI text ("templated and AI descriptions side by side"), but the CSVs that AC-1, AC-3 (checksums), AC-7 ("descriptions share no full template sentence"), AC-9 (data dictionary) and the AC-2 hard-negative case all check need a single description column. If the build publishes templated text, AI text only feeds the pack. If both are published, there are two columns, and the hard-negative and leakage checks must say which one they run on. As written, two implementations that publish different columns would both pass. -> State it explicitly. For example: "the build publishes templated `description`; AI text is read only by `sample-pack` (or published as a separate `description_ai` column listed in the data dictionary)". Then name the column that AC-2's hard negative and AC-7's sentence check run on.
2. [major] AC-4 doesn't cover free text, which is the most likely place for real names. "when any output CSV contains an institution, person, vendor or system name ... the name comes from the lists" can only check name columns. Template sentences and, above all, LLM-written risk, control and issue descriptions can easily mention real core-system or vendor names (the kind of name the deny-list exists to catch). That would break INV-9 and a stated non-goal, and AC-4 would still pass. -> Extend AC-4: every text cell in every output CSV, the committed AI text file(s) and `sample_pack.md` contains no deny-list token (case-insensitive, whole-token). Also say how the test finds name columns, for example columns marked as names in the data dictionary.
3. [major] AC-1 contradicts the epic and is unclear about the shared edge labels. "one CSV ... per relationship type in the ER diagram (excluding CANONICAL_* and maps_to)" still requires an `ia_maps_to_erm` CSV. The epic says that edge is E2 output and that E1 writes it only in the answer key (`taxonomy_map.csv`), and the plan's own Data impact list leaves it out. Also, `owned_by` (ISSUE->PERSON, CONTROL->PERSON) and `against` (ISSUE->CONTROL, ISSUE->RISK) each appear twice. AC-11 treats them as separate files ("ISSUE against", "ISSUE owned_by"), but AC-1 doesn't say whether there is one file per label or one per (from, label, to). -> Exclude `ia_maps_to_erm` in AC-1. Define relationship files as one per (from, label, to) triple from the diagram, so the test can list exactly 16 edge files.
4. [minor] AC-2 says answer_key/ "contains at least one ... hard negative", but the answer-key schema has no hard-negative field. A hard negative is derived, under the epic's definition, from TF-IDF cosine against the median of true matching pairs. -> Reword: the test computes hard negatives from the published descriptions (see issue 1) and the answer key, using the epic's definition, and finds at least one for risks and one for controls. With only a few true pairs at sample size, note that the median is taken over those few pairs.
5. [minor] The 1-20 row cap fights the "both taxonomies" goal. ERM's Basel-style L1 alone has 7 nodes, so ERM L1-L3 plus IA L1-L3 in one TAXONOMY_NODE CSV of at most 20 rows forces bare one-child chains. The owner may then mark the taxonomy "not realistic" for reasons that belong to child b, which triggers a needless revise loop under the epic's partial-pass rule. -> Either allow a higher cap for TAXONOMY_NODE (and for `parent_of`), or have the review table tell the reviewer that taxonomy depth and breadth are b's and are not judged here.
6. [minor] AC-8 names a committed path as its output ("writes research/r2-synthetic-text-realism/sample_pack.md"). A test that does exactly that overwrites a committed research file on every run. The plan also doesn't say how the pack and the owner's verdict reach the base branch, where research knowledge must live (rule 9) and where b's GO gate is checked. -> Give `sample-pack` an `--out` option (default: the research path) and have the test write to a temp dir. Add a line saying the pack and decision.md are committed to the base branch (or brought home with `capitan rescue`) before the gate is judged.
7. [minor] AC-11's override has no stated interface ("the ISSUE count overridden (e.g. 5 ...)"). AC-1 shows only `--size/--seed/--out`. -> Name the mechanism, such as a `--count ISSUE=5` flag or a documented function argument, so the test and b-e use the same hook.
8. [minor] AC-6's failure cases need a way to inject missing, stale or orphan text without editing the committed files, and the plan doesn't give one. Otherwise the test either changes the repo or can't run the "build fails" cases. -> State that the build accepts a text-directory override (or reads text from a path the test can point at a temp copy).
9. [minor] The leakage test (AC-7) checks ID numbers, sentences and attributes, but not the epic's other leakage rule: "IDs and row order shuffled independently per source". An implementation that writes ERM risk i and its IA match at the same row index passes AC-7 and gives E2 a free signal that b-e would inherit. -> Add one assertion to AC-7: matched cross-source items don't sit at the same row index in their source's CSV, or row order isn't the generation order.
10. [minor] The timebox is tight. Two days covers 11 criteria, about 15 entity and edge generators, a six-case answer key, a data dictionary, a one-off AI run and a renderer. The plan already names the split (AI text into its own change). -> Decide up front which slice is cut first if day 1 ends before slice 4. Slice 6 is the natural cut, since templated text alone still gives the owner a reviewable pack.
Not checked: whether capitan's gate counts `.gitattributes` or `akg/**` as governance or outside the epic's areas (the epic lists them, so they look fine); whether the deny-list's content is adequate (it's described as a floor); whether the owner can judge realism from ~15 rows (by design, a manual gate).
