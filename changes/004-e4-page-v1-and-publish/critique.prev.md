VERDICT: REVISE
1. [major] The allowed-numbers rule is checked in the wrong place. "The template and the JS hold no result figure: a test allows only a listed set of literal numbers in them ... and fails on any other digit run." The figures are now rendered by the Python builder, which is not scanned, so a figure typed into `build.py` (an f-string, or a dict of fallback values) gets past both tests: it is not in the template, and it carries no `data-source` mark, so the marked-figure check never sees it. As written, the rule also cannot work on the files it does name. The template holds the CDN pins (`cytoscape@3.x.y`, SRI hashes), and the CSS and JS need layout numbers (px, colours, zoom, node sizes), so the allow-list would fill with noise. -> Run the digit check on the **rendered** HTML. Take the visible text nodes with `html.parser`, skip `script` and `style` and attribute values, and remove every `data-source` element. Any digit run left over must be on the allow-list. That covers the template, the builder and the copy in one stdlib test. For the JS, test what matters instead: no `fetch`/`XMLHttpRequest`, and no writes to `textContent`/`innerHTML` that carry digits.
2. [major] The headline result is written in words, so the digit rule cannot catch it. The headline is "SQL once (round 5) ..., graph three times (rounds 1, 6, 7) and close three times ...; six of seven differ from the verdicts expected", plus "the rounds within one point named (1, 3 and 7)". These are the page's most important claims (O1's top section, O2's "no claim without a test"), and as copy they pass every listed test: number words are not digit runs, and "rounds 1, 6, 7" will likely just be added to the allow-list as round numbers. If a round's verdict changes, the headline goes stale silently. -> Have the builder render these counts and round lists from `rounds.json` (verdict tallies, rounds with margin within one point, count of measured != expected) inside `data-source` elements. Name a test that recomputes each of them from the export. Number words in those sentences count as figures.
3. [major] `src/features/rounds/symmetry.py` falls outside child a's areas. Child a's areas are `src/features/site/**`, `tests/**`, `docs/**`, but the Shape says "020's construct snippets move from the test into `src/features/rounds/symmetry.py`". The pre-commit gate will flag the file, and the `rounds` feature README (one README per feature folder) would need a line for the new module. -> Add `src/features/rounds/symmetry.py` and `src/features/rounds/README.md` to child a's areas. Also state that no other file in `src/features/rounds/` changes (E3 is closed).
4. [minor] L-021 is kept only if the moved test still pins the whole table. Today the test iterates over a literal dict, so dropping a construct changes the test itself, which a reviewer sees. Once the snippets move out, a construct removed from `symmetry.py` (or one added without a triple) would pass silently if the test iterates over the generated table. The "moving parts follow one rule" assertion, which depends on `"disclosed"` in the construct name, could also lose its anchor. -> The test keeps a literal `{construct name: (sql triple, cypher triple)}`. It asserts that the generated table's construct names equal that set in both directions, and that the committed site-data table equals both `symmetry.py`'s live output and the literals. It keeps the same-moving-parts check for every construct not named as disclosed. Then a snippet edit that changes a triple still fails, and the page cannot show a snippet the test does not pin. A snippet edit that keeps its triple passes, which is acceptable because the page shows the same snippet the triple was computed from.
5. [minor] Composite and formatted figures have no defined match rule. `data-source="rounds.json:rounds[4].scores.sql"` works for one field (checked: `rounds` is a list and `rounds[4].scores` is `{sql: 29, cypher: 41}`). The page also shows "33/33", "+4.75", "20 of 61 rows", precision as a decimal or percentage, and tallies (issue 2), each of which joins or reformats fields. "Every marked figure equals its source" is undefined for these, and an implementer will either skip marking them or write a second formatter inside the test. -> Have the builder use one small set of named formatters (for example `signed`, `fraction`, `of_n`). Let a mark name its formatter and fields (`data-source="scores.json:risk.auto_merged.precision" data-format="fraction"`). The test applies the same formatter from the builder module to the export values. Derived figures (tallies, "within one point") either live in the site-data export or use a named derivation that the test recomputes on its own.
6. [minor] The Pages workflow "runs the site builder on the committed exports on each push to main and deploys its output". Nothing says the deploy waits for the tests, so a push whose exports fail their currency or figure tests (for example a stale `rounds.json` after a rule change) is still published. -> Gate the deploy on the test job: `needs:` in one workflow, or `workflow_run` on `tests.yml` with `conclusion == 'success'`. State this in c, since the owner commits the file.
