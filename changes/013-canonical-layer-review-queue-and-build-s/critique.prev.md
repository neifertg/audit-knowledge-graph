VERDICT: REVISE

The plan fits the epic. The mirror rule answers the epic critique's item 1 and its "no canonical risk holds two IA risks" check. The merge rules match the scratch measurement (`e2c_measure.py` sorts by (-score, (erm_id, ia_id)) and applies the same greedy rule), and CI does not run tests yet, so the cross-platform signal in E3 is believable. What is left is mostly about pinning the output files, because a byte golden freezes whatever the implementer happens to choose. One test also cannot fail.

1. [major] Six decimals erase the merged scores. `scores written with 6 decimals` and `score in the maps-to files is the merged edge's score`: the committed weights put the auto-accept thresholds at 0.99993637 (risks) and 0.99999658 (controls). I measured seed 42 with the merged `pair_scores`. The 68 accepted control scores print as only 4 distinct values, and 27 of them print as `1.000000`. The 38 accepted risk scores give 24 distinct values, 5 of them `1.000000`. A reader (O2), E3 and child d cannot rank or compare merged edges from these files. A test that reads bands back from the CSV is also comparing rounded numbers against unrounded thresholds. -> Write a score with room near 1, such as the logit `z` or `-log10(1 - p)`, with fixed decimals, or write p with enough significant digits. Say which one in AC-1, and state that bands and the merge order use the unrounded value.
2. [major] Some output rules are not pinned, so the golden would freeze choices the plan never made:
   - (a) A canonical control holds one ERM control and any number of IA controls. Which score goes on the ERM control's `control_maps_to_canonical` row: the highest of its merged edges, or something else?
   - (b) "Rows sorted by their first column" does not settle the order. That column is not unique in `risk_maps_to_canonical`/`control_maps_to_canonical` (`source`) or in `review_queue` (`kind`).
   - (c) The values of `kind` are not given (`risk`/`control`/`duplicate`?), and neither is which item is `item_a`: ERM first for cross-source pairs, and the lower ID first for duplicates?
   - (d) `drivers`: "largest coefficient x value" does not say whether it means signed or absolute contribution. It also does not say the output order, the tie-break, or that features are named by `weights.json`'s `columns`.
   - (e) "Lowest member ID" should say plain string order (`ERM-…` sorts before `IAR-…`).
   - (f) The merge order says "then pair IDs", while the epic says "lower source ID". State it as (ERM ID, IA ID), as the scratch script does.
   -> Pin each of these in AC-1/AC-2, sorting every file by its full key, and have the AC-1 test assert the sort order and the `kind`/`reason`/`placement` value sets.
3. [major] The AC-4 test cannot fail. If `akg reconcile` exits 0 but writes nothing, or skips files it finds already there, the comparison still passes. -> Delete both `answer_key/` and `reconciled/` from the copy before running `akg reconcile`, and assert that every expected file was recreated.
