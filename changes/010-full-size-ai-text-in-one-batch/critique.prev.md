VERDICT: REVISE
1. [major] The issue-opening rule needs a prompt the sample never used, and the plan does not say how the prompt version in the hash treats the sample. Data impact says "the same rules as the sample (L-002)" and "Issue descriptions keep their four openings as the draft's first words", and AC-3 enforces that openings rule. The current prompt does not ask for it. The issue `VOICE` says only "one to three sentences stating the condition found", and `system_prompt()` says "Do not reuse any full sentence from the draft", which pushes the model to reword openings. Measured on the committed sample: 15 of 15 AI issue texts drop their draft's opening words ("Second-line testing found that ..." becomes "During second-line testing of ...", and 7 of 10 IA and 2nd-line texts become "Internal Audit found that ..."). That leaves two outcomes, and the plan chooses neither:
   (a) The prompt is left unchanged. Most of the 250 issues then fail AC-3 twice and are blocked, so AC-5 cannot pass.
   (b) The issue voice or system prompt is changed. The full set's prompt version then differs from the sample's. AC-3 puts "the prompt version (a hash of the system prompt and voices)" in each entry's input hash, and the build computes `TextItem.input_hash` for both sizes (`generate.py`, `_apply_ai_text`). If the version enters the hash at sample size too, all 75 committed sample entries become stale. The sample build, `test_ai_text`, `test_offline` (`--text ai`), the sample golden and the committed `sample_pack.md` then fail. That contradicts "the sample golden is unchanged" and AC-4's "the sample's check-text still passes", unless the sample is regenerated, which is paid, outside the $10 cap, and changes the sample golden.
   -> State in AC-3 the prompt text that enforces the openings (a sentence for the issue voice, and an exception to the "no full sentence" rule for the opening words). Say how the prompt version is scoped. Either each size's text file records its own prompt version (the sample keeps the version it was written with, which is a stated exception to L-002 because the sample and full sets are separate), or the sample is regenerated and its golden and pack are updated within the budget. Add a test that the sample build still passes with its committed file after the hash change.
2. [major] The budget guard can still fail open at submission time. AC-1 says "a row is written at submit time with the estimate (status `submitted`) ... and records the batch ID". If the row is written after `batches.create` returns, a crash, a timeout or a lost response after the server has accepted the batch leaves no row. A re-run then sees $0 for a batch that will be billed, and two full passes (about $10) both pass the check. The same thing happens when the log is missing: "a missing log means no spend" is open by default. That case arises if `cost_log.md` is resolved relative to the working directory rather than the module, or if the run happens on a checkout where the `change/010` log is not committed (knowledge lives on the base branch, the run happens on the change branch). A row whose status is neither `submitted` nor `collected` (for example `canceled` or `expired`, which can still bill partially) is not covered either.
   -> Write the row with status `submitting` and the estimate before calling the API, and count it as spend until it is resolved. Fill in the batch ID after the call succeeds. Resolve the log path from the module, as `TEXT_DIR` is resolved. Refuse on any unknown status. After the client exists and before any submission, check the account: list the account's message batches and refuse if any batch is missing from the log. That makes the API, not the file, the backstop for "missing log" and "crash after submit". Name a test for the `submitting` row and one for an unlogged batch reported by the fake client's `list`.
3. [minor] The $10 cap applies to estimates, not to actual charges, and the plan does not state the worst case. AC-1 refuses a run "when spend plus estimate exceeds the budget", and Data impact says "The script refuses any run that would cross the cap". With `max_tokens` 1000 and batch prices of $2/$10 per MTok, one item can cost up to about $0.00194 input + $0.01 output = $0.012. A full pass of 1,274 items is then bounded at about $15.3, not $10. The 1.25-margin estimate ($6.26) passes the check whichever way the pass turns out. The realistic risk is small, since the measured average is 199 output tokens, but the claim as written is not true. -> Either size `max_tokens` so the worst case fits the cap (for example about 450 tokens puts a full pass at about $8.2; a truncated item becomes a `max_tokens` failure and is resubmitted), or keep 1000 and say in Data impact that one pass can exceed the estimate up to about $15 and that the owner accepts that. For the resubmission batch, have the guard use the worst case (items x (input + `max_tokens`) at batch prices), because by then actual spend is known.
4. [minor] The AC-1 tests can pass with a guard that ignores uncollected rows, or with one that refuses on the estimate alone. The described case is "about $6 logged plus a $5 estimate against $10". If that $6 row is `collected`, an implementation that sums only `actual_usd` passes, and the open path the previous critique found (an uncollected batch counted as $0) goes untested. There is also no accept case with the same $5 estimate, so a guard that refuses any estimate near $5 still passes the refusal test. -> In `test_ac1_over_budget_refused_before_any_client`, cover three cases with the same $5 estimate: a `submitted`-only row with a $6 estimate and no actual is refused; a `collected` row with $6 actual is refused; and an empty log is accepted, which reaches the fake client.
5. [minor] `test_ac6_tests_never_import_anthropic` cannot catch the import it exists for. AC-6 says it "imports every test module in a subprocess and asserts `anthropic` is not in sys.modules afterwards". Importing a module does not run its tests. The risk is in the run path that the batch tests call with a fake client. The current `main()` does `import anthropic` there, and catches `anthropic.APIError`. An implementation that keeps that import passes this test, because `anthropic` is installed in the venv. -> Run the batch test cases themselves in the subprocess (for example `unittest` on `generator.test_batch`, excluding this test), then assert. Or require the client and its error type to come from an injected factory, so the run path never names `anthropic`.
6. [minor] The published cue figures can still go stale in docs/data-model.md. AC-5's test compares the build with `tests/golden/cue_figures.json` (tolerance 0.01), but the figures readers see are the ones "quoted in docs/data-model.md". Nothing checks that the doc matches the JSON, so the doc can keep old numbers while the test is green. -> In `test_ac5_published_cue_figures_match_the_build`, also assert that each JSON figure appears in docs/data-model.md at the stated rounding.
