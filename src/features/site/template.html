Supporting evidence

What is a knowledge graph?

A knowledge graph stores facts as nodes and the links between them: things such as systems, controls, risks, issues, auditable entities and business units are nodes, and each relationship, such as "this control mitigates that risk" or "this control depends on that system", is a link you can follow from node to node. A relational database can hold the same facts in tables, with each relationship as a row in a link table. Here, both stores hold exactly the same links. What differs is how a query is written: a question that follows a chain of links, such as "what does this system's failure reach?", is a path in the graph and a series of joins in SQL. The comparison below counts how much query each needs; for that question, both come out close.

What was merged, and what is waiting

Auto-merge uses a training-bank precision target of {{scores.json:threshold_targets.auto_accept_training_precision}}. Merged precision is {{scores.json:risk.precision.count}} for risks and {{scores.json:control.precision.count}} for controls. Merged recall is {{scores.json:risk.recall.count}} for risks and {{scores.json:control.recall.count}} for controls. If a reviewer resolves the queue correctly, recall would be {{scores.json:risk.recall_if_resolved.count}} for risks and {{scores.json:control.recall_if_resolved.count}} for controls. The review queue holds {{scores.json:review_queue.total}} pairs. The matcher's thresholds are deliberately conservative, so most true matches wait in the review queue rather than being merged silently.

The data is synthetic, from a single generator and a single bank, with small samples. The training bank comes from the same generator, so its weights know the generator's habits. No speed or scale claim is made.
